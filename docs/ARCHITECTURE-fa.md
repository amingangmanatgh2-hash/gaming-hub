# معماری فنی هم‌کلام

## ۱. تصویر کلی

```
                        ┌──────────────────────── Cloudflare Edge ────────────────────────┐
   مرورگر A ──HTTPS──►  │  Assets (public/)  ← HTML/CSS/JS/آیکون/SW                       │
                        │  Worker (worker/index.js)                                      │
                        │     ├── /api/*  → shared/api.js  (health, config, ice, room)    │
                        │     ├── /r/CODE → صفحهٔ اتاق                                    │
                        │     └── /api/ws → Durable Object «Room» (WebSocket hibernation) │
                        └────────────────────────────────────────────────────────────────┘
       مرورگر A ◄─────── WebRTC (صدا/تصویر/فایل زنده) ───────► مرورگر B   [P2P، بدون سرور]
```

* **سیگنالینگ و وضعیت اتاق**: یک Durable Object به‌ازای هر کد اتاق.
* **رسانه**: WebRTC mesh مستقیم. سرور هیچ‌وقت صدا/تصویر را نمی‌بیند.
* **فایل بزرگ**: از همان کانال دادهٔ WebRTC (چانک ۲۴KB روی سوکت سیگنالینگ به‌صورت base64 برای سادگی و پایداری).

## ۲. چرا WebSocket Hibernation؟

کلاس `Room` از `state.acceptWebSocket()` استفاده می‌کند. یعنی:

* سوکت‌ها باز می‌مانند، ولی وقتی پیامی ردوبدل نمی‌شود، DO از حافظه خارج می‌شود ⇒ **هزینهٔ CPU صفر**.
* متادیتای هر عضو (نام، نقش، وضعیت میکروفن/دوربین، دست بلند) با
  `ws.serializeAttachment()` ذخیره می‌شود تا بعد از بیدارشدن هم در دسترس باشد.
* `state.getWebSockets()` فهرست اعضای زنده را می‌دهد؛ همهٔ منطق (نقش‌ها، میزبان، در انتظار) روی همان حساب می‌شود.
* یک `alarm` برای دو کار: **پاک‌کردن اتاق خالی** و **پایان عمر اتاق**.
* داده‌ها در `storage` (SQLite-backed در migration v1) می‌مانند: چت (۲۰۰ پیام آخر)، یادداشت، نظرسنجی، تخته.

## ۳. پروتکل (خلاصهٔ JSON)

از کلاینت → سرور:
| `t` | کاربرد |
|---|---|
| `join` | ورود با کد، نام، رمز، حالت‌های اولیه |
| `s` | سیگنالینگ: `{to, d:{sdp|cand|f}}` — `to:"*"` یعنی پخش (فایل زنده/واکنش) |
| `chat` / `chatop` | پیام و عملیات (ویرایش/حذف/سنجاق/واکنش) |
| `state` | میکروفن، دوربین، اشتراک صفحه، در حال تایپ، وضعیت زیرنویس |
| `hand`, `react`, `typing` | دست بلند، واکنش، در حال نوشتن |
| `host` | دستورهای میزبان: `kick, ban, mute, muteall, cameraoff, lock, waitingroom, setttl, transfer, approve, deny, end` |
| `poll`, `notes`, `wb`, `sub` | نظرسنجی، یادداشت، تخته، خط زیرنویس |
| `ping/bye` | ضربان و خروج |

از سرور → کلاینت: `welcome` (تاریخچه+اعضا+وضعیت کامل)، `pjoin/pleave`، `s`، `chat/chatop`,
`state/hand/typing/react`، `knock/waiting`، `room` (تنظیمات/نقش/هشدار پایان عمر)، `poll/notes/wb/sub`،
`sys`، `err`، `bye`.

سقف‌های محافظتی در `shared/protocol.js` (`LIMITS`): ۴۰۰ پیام در دقیقه برای هر نفر،
۶۴KB برای هر پیام، ۲۰۰ پیام تاریخچه، ۱۵MB سقف فایل زنده و…

## ۴. WebRTC: چرا mesh و چطور سبک می‌ماند؟

* **دو m-line آمادهٔ اولیه** (audio + video) ⇒ خاموش/روشن‌کردن میکروفن و دوربین فقط
  `replaceTrack` است، نه `renegotiation` ⇒ بدون پرش تصویر روی اینترنت ضعیف.
* اشتراک صفحه دو m-line اضافه (`sendonly`) می‌سازد و بعد از پایان، فقط ترک‌ها خالی می‌شوند
  تا بار بعد بدون مذاکرهٔ مجدد برگردد.
* **مذاکرهٔ مودبانه**: هر دو طرف `onnegotiationneeded` دارند؛ برنده بر اساس مقایسهٔ شناسه‌ها.
* **Restart ICE** روی `failed` ⇒ ترمیم خودکار بدون خروج از جلسه.
* سقف نرخ بیت/رزولوشن از پروفایل‌ها می‌آید:

| پروفایل | رزولوشن | fps | سقف ویدئو | یادداشت |
|---|---|---|---|---|
| `audio` | — | — | ۰ | فقط صدا؛ کم‌مصرف‌ترین |
| `lite` | 320×180 | 12 | 80 kbps | اینترنت ضعیف |
| `normal` | 640×360 | 20 | 220 kbps | پیش‌فرض |
| `hd` | 1280×720 | 24 | 1100 kbps | اینترنت پرسرعت |

`QualityMonitor` هر ۶ ثانیه تأخیر/افت بسته را می‌سنجد و در صورت نیاز **خودکار** پروفایل را سبک‌تر می‌کند.

## ۵. فرانت و بهینه‌سازی ایران

* هیچ فونت/آیکون/کتابخانهٔ بیرونی: ۰ درخواست خارج از دامنه.
* esbuild → یک فایل JS برای هر صفحه (صفحهٔ اصلی ~۱۴KB gzip، اتاق ~۴۲KB gzip).
* `<link rel=manifest>` + Service Worker سبک (کش فایل‌های ثابت، هرگز `/api/*`).
* همهٔ متن‌ها RTL و فارسی؛ `prefers-reduced-motion`, `prefers-color-scheme` و برچسب‌های دسترس‌پذیری رعایت شده.
* حالات کم‌مصرف: پروفایل کیفیت، «داده‌کم» (خاموش‌کردن ویدئوی دریافتی)، خواب نرفتن صفحه (Wake Lock) برای جلسات طولانی.

## ۶. آزمون‌ها

```bash
npm test
```
1. **protocol.test.js** — کد اتاق، ICE/TURN، یکتایی قابلیت‌ها.
2. **dom.smoke.test.js** — با jsdom: صفحهٔ خانه و اتاق بدون خطای JS بالا می‌آیند،
   و همهٔ `#id`های استفاده‌شده در باندل، در HTML وجود دارند.
3. **signaling.e2e.test.js** — سرور توسعه را بالا می‌آورد و با دو کلاینت واقعی WebSocket
   ورود، همتاها، چت، تایپ، دست، وضعیت، واکنش، سیگنالینگ WebRTC، پخش فایل زنده، نظرسنجی،
   یادداشت، تخته، انتقال میزبانی، اخراج، قفل، اتاق انتظار و فایل‌های استاتیک را می‌سنجد.

علاوه بر این‌ها، مسیرهای Durable Object روی **workerd واقعی** با `npm run dev:worker` آزمایش شده‌اند
(`wrangler dev` محلی): ساخت اتاق از REST، اتصال سوکت، ماندگاری چت/یادداشت/تخته/نظرسنجی پس از خروج،
انتقال میزبانی و تحویل میزبانی به نفر تازه.
